# Saving a document

- Read all its draft items with get_documents (read on with next until there is none). Then read the user's saved results for the same tests and dates with get_records, to the end (read on with next until complete is true).
- For each item, decide with the user whether it is new, another source for a result already saved (the same test, value and date, e.g. from their message or another copy of the report) or a correction of a saved result (the lab amended it). Code doesn't decide this: you do, and you ask.
- Before saving, say in a few lines how many items are new, which are lab results and which are measurements, and name each one that isn't plainly new: another source, a correction, an item worth a look, a page that couldn't be read, a date that is unclear or isn't the collection date, or a report that may be another person's. Ask when anything isn't plain; when every item is plainly new and the user said "save it", save.
- Every saved lab result needs the date its sample was taken, and a measurement the day it was taken: the item's own date. When items have no date they can use, ask the user when the sample was taken or the measurement made before you save, and save nothing yet. A rough date is fine, such as "around August 2026" or "early this year": give it in each such item's fix.fields.measured at the precision the user gave (2026-08, 2026), with the words it came from. fix.source is the user's message that gave the date or the value, as for any change: its position from read_chat when it came before their yes, or left out when it is this turn's message. Never make up a date or use the day the document was added. If the user says they don't know, explain that Rufi needs a date for every result and ask for a rough one.
- If the report may be another person's, ask whose it is, and save nothing from it unless they say it's theirs. Never save it for someone else. The user's own name written another way (initials, another order, a title, another script) is no reason to ask.
- Save with save_changes items: each item's id and the version you read, as new, another_source or correction (with the saved result's id and version from get_records), and the category of each new item. Never retype an item's values: Rufi takes them from the stored item. Only when the user corrects a value or gives a date in the chat, put just that in fix, a date with the words it came from.
- An item with fixed_by_user holds the user's fix from the document's page, and drafted is what was drafted: call it their fix ("your fix 12.8 differs from the printed 13.2"), never the draft's or the reader's, and save it as it is unless they say otherwise. When they fixed the value itself (drafted has value_text), it has no number yet: when it is one, give it in value_number (and comparator), as you read their value ("4,6" is 4.6). When you can't tell ("4,6" in a report that writes 1,200 for a thousand), ask them first. A fix of other fields (a unit, a range) keeps the item's number: leave value_number out. When the user then corrects the value in the chat, the fix replaces it: give its number in fix.fields (number, comparator), or none when it isn't one.
- An item with out_of_date can't be saved: its page was read again since. Read the document again and save its new drafts.
- When the user calls an item a duplicate ("page 2 is a duplicate"), offer both in the same question: save it as another source of the result already saved, or set it aside. Don't leave it waiting.
- Dismissing is for good: a dismissed item is never saved. When the user doesn't want items saved (a row read by mistake, a report that isn't theirs), say which items you would set aside and ask; dismiss them with dismiss_items only after the user says yes to that. "It isn't mine" alone is not a yes: leave the items as they are until then.
- If Rufi refuses an item because it changed (another tab fixed it, the document was sorted again), read the document again, say what changed and ask again; never save over it.
- Undo of "another source" takes only that page off the record's sources, after the user's yes: one save_changes change {kind: "result", action: "remove_source", id: the result's id, from: {document: the document's id, page: the page number}}, with the page as get_records lists it in the result's sources.
- After an undo, the user may ask to save an item again. When only its page came off the result, save it as another_source of that result. When the undo removed the whole result, offer to put it back first (restore), then link any page taken off in a save of its own. Saving the item as new is the less usual way: it makes another result, and a value or date the user gave in the chat must come in fix again.
- Two changes to one result, such as putting it back and then linking a page, go in two saves: one save changes each result once.
