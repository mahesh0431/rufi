# 0006 · The AI's queries see one person's record, by construction

**Date:** 8 Oct 2026 · **Status:** accepted

`run_sql` gives the AI one read-only SQLite query on the record of the conversation's person, chosen by Rufi, never by the AI. For each query Rufi copies that person's rows of the record tables (`RECORD_TABLES` in `core/store/scoped.ts`: their `people` row, documents and the files those name, reports, results, the other record kinds, and their saves with each record's before and after) into a new in-memory database, in one synchronous read so that no save lands in between, and the query runs only there. Conversations, settings, drafts and other people are never copied, so no query can reach them, whatever it says. Every table is in that list or in Rufi's own; a test fails for a new table in neither. Removed records and replaced results are copied too, marked as they are. The query runs in a child process with no environment, which Rufi kills at the time limit (5 s): SQLite can't be interrupted from Node, and a thread running SQLite can't be stopped. The child runs the query in a worker thread, so its own main thread can still end the process a second after the limit, or at once when the core is gone. There, SQLite's authorizer allows only reading (select, read, functions, recursive queries: no attach, pragma, transaction or write), `query_only` is on, SQLite's heap is capped, and text after the first statement is refused unless it is only comments. At most 200 rows and 32 KB of rows (as UTF-8 JSON, under what Codex passes on to the model whole) come back; a cut result says that it is cut and why, and a failed or stopped query gives no rows, only its error, which doesn't use up the turn's rejections. The reason: the person's scope is one of the few things that must never go wrong, and a copy makes it true by construction rather than by checking each query; the AI writes the SQL, and code bounds what it can see and what it can cost. The cost: a child process (about 50 ms) and a copy of the record for each query, which is fine for one person's record today and to look at again if records grow large (documents, M3). Two reads in one reply copy the record twice, so a save between them can show both states; their results are kept, and this race is accepted.
