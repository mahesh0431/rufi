# 0009 · Documents are read in the background by a Rufi sub-agent, one job at a time

**Date:** 10 Oct 2026, its models 11 Oct 2026 (ADR 0010) · **Status:** accepted

A document is read by a background job, outside the chat, by a **Rufi sub-agent**: an AI thread that Rufi starts, binds and checks itself, not the agent's own sub-agents (those inherit the chat's access and settings). The job table (`jobs`, `core/documents/reading.ts`) is built once for every kind of background work; reading is its first kind. Jobs run one at a time, oldest first, as each document is added (the first run tells the person that documents go to the AI provider; nothing falls back to another service). Each job targets pages of its document (all of them first; a retry only the pages that failed), and each run of it is a new attempt. The reader (`server/reader.ts`) runs on the private runner (`agent/codex/subagent.ts`, ADR-level rules in `AGENTS.md`): a fresh ephemeral thread with Rufi's reading instructions in place of the agent's, no history, files, commands, network or other sub-agents, and exactly two tools bound by code to this person, document and attempt: `get_page` (the page image, the PDF's own text, the page's current entry, the note and progress) and `save_page` (one page's entry and the note, in one transaction, only for a target page looked at since the last compaction). The work lives in the database, in the reading's **notebook** (an entry per page and one note), never in the thread, so a compaction or a crash loses nothing: after a restart the job is queued again and its next run continues with the targets that have no entry; if every target has an entry from a run not recorded as failed, code finishes without a reader. Each entry stores its attempt. Requeuing or failing a run marks that attempt's entries as failed in the same transaction, without changing their contents. They remain in the notebook for Retry, which must get a normally completed turn before publishing them. Code checks each entry as it is saved and only flags it (a row count that differs from the items: "may be incomplete"; a number that isn't its printed value, or a value missing from the PDF's own text: "unsure"); it never corrects or rejects a value, and the reader is told what was flagged. **Only a reader turn that completed normally finishes a job**: the run is closed to writes first, then one transaction writes the target pages' states (a page with no entry is "not looked at"), the draft items from this job's entries (version 1, the reader's fields kept), the document's kind and date when every page agrees, its version raised, the job done, and the chat's end line as a Rufi event, with a note for the AI only when something needs the person. A failed, interrupted or late turn keeps the entries and makes no drafts: a passing failure (a lost connection, a restart) gets one automatic retry; sign-in and usage limits make the job wait visibly; anything else fails it with its end line, and Retry continues it with a fresh deadline (5 minutes plus one a page, at most an hour). The reader's version (instructions, entry format, model, effort, page preparation, tools) and the AI use are stored with each job. Considered: reading inside the chat turn (blocks the chat, lost on Stop); one AI call per page (headings and dates lost between pages); one answer at the end (a compaction or a crash loses the work); the chat AI starting readers (every document is read anyway, and the Documents page has no turn); a sandbox folder with a shell (the agent's sandbox can read outside it); a separate finish tool (the end of the turn is the finish). The reason: reading is slow and safe to repeat because it changes nothing in the record, so it belongs in a retryable job, while every decision stays in the chat. The cost: one reading at a time (twelve reports wait their turn), the reader runs only on models whose complete set of tools Rufi has pinned and tested (ADR 0010), and a reading can't be stopped yet.
