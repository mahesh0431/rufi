# 0014 · Where Rufi keeps its data: a remembered folder, moved only by a checked copy

**Date:** 11 Oct 2026 · **Status:** accepted

Rufi's home is `~/.rufi`, one folder for everything Rufi keeps: it holds the location file, `~/.rufi/location.json` (`{version: 1, dataFolder}`, an absolute path, nothing else), the default data folder `~/.rufi/data`, and later what belongs to Rufi rather than to one record (skills, customizations). The data folder holds the record, documents, backups, the AI's files and workspace; a move takes `data` elsewhere, and the location file stays in `~/.rufi`, so a lost disk can't take it away. One resolver, `findDataFolder` (`core/store/data-folder.ts`), decides for the core and every terminal command, before any data-folder lock or database is made: a non-blank `RUFI_HOME` picks its folder and the location file is never read or written (demo, tests, the test sign-in and restored copies stay apart from the person's data); otherwise, under `location.lock` in `~/.rufi`, it opens the folder the location file names.

An older Rufi app also used `~/.rufi`, with a person's real data, and never wrote a location file. So with no location file, a home that holds any name but `data`, `location.lock`, the location file's temp file or Finder's `.DS_Store` (Show in Finder can leave one) stops Rufi before any lock: nothing in it is read, moved or changed (only names are looked at). Once this Rufi has written its location file, the home is its own, and names put beside it later (the older app run again) are left alone and don't stop it. This guard also checks chosen and remembered paths, and both paths of a move, that resolve into `~/.rufi`, including aliases, before any mark is read. The restore command checks its resolved backup and target paths with the same guard before reading the backup or taking the target lock. A named folder that is gone, isn't a folder, or has no `installed.json` stops Rufi with the path and what to do; so does a damaged location file. Nothing is made in their place: an unplugged disk must never turn into an empty record.

With no location file, an absent or empty default folder starts a record under its `rufi.lock`. Before making the database, `openRecord` durably writes `creating.json` (`{version: 1}`) beside it, only when both `rufi.sqlite` and `installed.json` are missing. This owns a first start that stopped: an uninstalled empty database may be initialized, and an interrupted `installed.json` temp file may be cleared after the marker is written again. With an owned, uninstalled database and its rollback journal, SQLite first rolls back the interrupted schema transaction before inspection; installed and unowned records keep the read-only gate. An unknown record is still refused. A `creating.json` temp file is recoverable only before any database exists. Once `installed.json` is durable, Rufi removes the creation marker and leftover bootstrap temp files, syncs the folder, and only then writes the location file (written whole, synced, renamed, and its folder synced). A complete default record is remembered again if the location file was lost; anything else stops Rufi. Deleting both the location file and the default folder can't be told from a new Mac; the help says so. The same creation gate applies with `RUFI_HOME`, without touching the location file.

| First-start state                                                                 | Next start                                                                                         |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `creating.json` temp file, no database or `installed.json`                        | Write the creation marker durably, then make the record                                            |
| `creating.json`, empty database, no `installed.json`                              | Roll back a bootstrap journal if present, inspect, then initialize the empty database              |
| `creating.json`, complete database, `installed.json` temp file                    | Inspect the record, write `installed.json` durably, then remove the creation marker and temp files |
| `creating.json`, complete database and `installed.json`                           | Use the normal installed-record gate, then remove leftover bootstrap files                         |
| Unknown database, or an empty database without ownership or with `installed.json` | Refuse; never initialize it                                                                        |

Moving is an offline command, `pnpm rufi move-data <folder>` (`core/store/move.ts`), with no Settings button yet. It refuses with `RUFI_HOME` set, while Rufi or a command holds the data folder's `rufi.lock`, and for a new folder that isn't absent or empty, is the data folder, is inside it or holds it (by real path), is in iCloud Drive or `~/Library/CloudStorage`, or is on a network disk (the Mac's mount list): an active SQLite record can't be synced or shared safely, while a closed backup can go anywhere. The cloud check is best effort, and the help names what it can't see. Under `location.lock` and both folders' `rufi.lock`, the steps are: mark the source `moving-out.json`, mark the new folder `moving-in.json`, copy, check, remove the new folder's mark, mark the source `moved-to.json` and clear `moving-out.json`, then rename the location file to the new folder. Each mark, and the location file, is written whole and synced with its folder; before the commit starts, every copied file and folder is synced, and so is each new folder's entry in the folder that holds it. The sync is `fsync`: it hands the writes to the disk in this order, but a disk's own cache can still hold or reorder them, so the order is established for a crash of Rufi or of the Mac, not proven for a power loss (a stronger flush, `F_FULLFSYNC`, is a TODO). Every start checks the folder's own marks, also with `RUFI_HOME`, so neither copy can take writes while a move is open. The copy takes everything but the locks, `core.json`, the marks, and the database's own files: `rufi.sqlite` goes through SQLite's backup (which takes in what its WAL holds) into a temp name, renamed when whole; its `-wal`, `-shm` or journal are never copied raw. The AI's own folders (`codex/`, `sub-agents/`) stay behind: Codex keeps absolute paths to this folder in its state database, and a thread resumed in a copy writes to the old folder's thread file, so the copy clears each chat's thread and the AI starts afresh with the saved chat, as after a model change (ADR 0004). A link or special file stops the move by name. The check: the database passes `checkDatabase`, every original it names is there with the SHA-256 its id names, and every other copied file has the source's SHA-256. (Until 31 Oct 2026) The Keychain entry is under `chatgpt.json`'s host id, not the path, so the moved folder stays signed in.

A failure the command sees before the switch cancels the move itself. A crash leaves a state that a start refuses and that `--finish` or `--cancel` ends, both under the same locks: `--finish` checks the copy again (never trusting an earlier check) and commits; `--cancel` marks the new folder cancelled for good, durably, then clears the source's marks, keeping every file of both. If the target is disconnected or its invalidation fails, cancellation refuses and keeps the source's marks until the target can be marked. Only ENOENT means a missing path; other lookup errors are thrown. After the switch, the location file names the new folder, which has no mark, so both are refused with "no move". The old folder is never deleted by Rufi.

| Source            | New folder                  | Location file | A start opens                    |
| ----------------- | --------------------------- | ------------- | -------------------------------- |
| `moving-out.json` | `moving-in.json`            | source        | neither                          |
| `moving-out.json` | complete                    | source        | the new folder, with `RUFI_HOME` |
| `moved-to.json`   | complete                    | source        | the new folder, with `RUFI_HOME` |
| `moved-to.json`   | complete                    | new folder    | the new folder                   |
| none              | `moving-in.json`, cancelled | source        | the source                       |

The desktop shell doesn't resolve the folder: it reads no server code and no file. It keys its Chromium profile (and so its one-app-per-folder lock) on `RUFI_HOME` when set, else on the remembered folder as a whole, and `rufi start` resolves the folder itself and tells Settings how it was chosen (default, moved or `RUFI_HOME`). Tests never reach the person's folder: vitest gives every test a scratch `HOME` (`tests/scratch-home.ts`), the resolver takes the home folder as a parameter, and the Electron fixture runs each app with a scratch `HOME`.

Considered: `~/Library/Application Support/Rufi` (the Mac's place for app data, but Rufi's home is meant to be easy to find in the terminal and to grow with skills and customizations); an editable path in Settings (one typo starts an empty record); following `RUFI_HOME` forever (every start needs the terminal); moving by rename (impossible across disks, and no point to check); copying `codex/` (proven to write into the old folder on resume); a pending move in the location file (invisible to a `RUFI_HOME` start); adopting an existing folder (`use-data`), deferred. The cost: a move copies the whole folder and reads every file twice; the AI's own history of the chat stays behind; a crash between the new folder's completion and the switch leaves a folder that `RUFI_HOME` can open and `--cancel` then retires; an older Rufi doesn't know the marks.

**30 Oct 2026: the agent database.** A move leaves `agents.sqlite` behind with `codex/`, whose conversations it names, and the moved folder starts it afresh (ADR 0024).

**31 Oct 2026: each provider signs in by itself.** Codex keeps its sign-in in `codex/` (`auth.json`) and Claude in `claude/` (`CLAUDE_CONFIG_DIR`; on macOS Claude keeps it in the Keychain under a name made from the folder's path). A move copies neither folder, so after a move Codex and Claude each sign in again. Claude's folder is never moved or renamed: Claude would look signed out. Rufi no longer has a sign-in of its own, `chatgpt.json` or `credentials.lock`.
