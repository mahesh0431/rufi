# 0014 · Where Rufi keeps its data: a remembered folder, moved only by a checked copy

**Date:** 11 Oct 2026 · **Status:** accepted

Rufi's home is `~/.rufi`, one folder for everything Rufi keeps: it holds the location file, `~/.rufi/location.json` (`{version: 1, dataFolder}`, an absolute path, nothing else), the default data folder `~/.rufi/data`, and later what belongs to Rufi rather than to one record (skills, customizations). The data folder holds the record, documents, backups, the AI's files and workspace; a move takes `data` elsewhere, and the location file stays in `~/.rufi`, so a lost disk can't take it away. One resolver, `findDataFolder` (`core/store/data-folder.ts`), decides for the core and every terminal command, before any lock or database is made: a non-blank `RUFI_HOME` picks its folder and the location file is never read or written (demo, tests, the test sign-in and restored copies stay apart from the person's data); otherwise, under `location.lock` in `~/.rufi`, it opens the folder the location file names. An older Rufi app also used `~/.rufi`, with a person's real data: so with no location file, a `~/.rufi` that holds any name but `data`, `location.lock` or the location file's temp file stops Rufi before the lock is taken, and nothing in it is read, moved or changed (only its names are looked at). A named folder that is gone, isn't a folder, or has no `installed.json` stops Rufi with the path and what to do; so does a damaged location file. Nothing is made in their place: an unplugged disk must never turn into an empty record. With no location file, the default folder decides: absent, empty, or holding only what a stopped first start leaves (a stale lock, a database before its marker) is a first start, which makes the folder (0700) and its record under its `rufi.lock`, and only then writes the location file (written whole, synced, renamed, and its folder synced), so a location file always names a folder with a record; a complete record (`rufi.sqlite` and `installed.json`) is remembered again, which recovers a lost location file; anything else stops Rufi and changes nothing. Deleting both the location file and the default folder can't be told from a new Mac; the help says so.

Moving is an offline command, `pnpm rufi move-data <folder>` (`core/store/move.ts`), with no Settings button yet. It refuses with `RUFI_HOME` set, while Rufi or a command holds the data folder's `rufi.lock`, and for a new folder that isn't absent or empty, is the data folder, is inside it or holds it (by real path), is in iCloud Drive or `~/Library/CloudStorage`, or is on a network disk (the Mac's mount list): an active SQLite record can't be synced or shared safely, while a closed backup can go anywhere. The cloud check is best effort, and the help names what it can't see. Under `location.lock` and both folders' `rufi.lock`, the steps are: mark the source `moving-out.json`, mark the new folder `moving-in.json`, copy, check, remove the new folder's mark, mark the source `moved-to.json` and clear `moving-out.json`, then rename the location file to the new folder. Each mark, and the location file, is written whole and synced with its folder; every copied file and folder is synced before the commit starts, so a power loss can't leave the location file naming a copy that isn't on the disk. Every start checks the folder's own marks, also with `RUFI_HOME`, so neither copy can take writes while a move is open. The copy takes everything but the locks, `core.json`, the marks, and the database's own files: `rufi.sqlite` goes through SQLite's backup (which takes in what its WAL holds) into a temp name, renamed when whole; its `-wal`, `-shm` or journal are never copied raw. The AI's own folders (`codex/`, `sub-agents/`) stay behind: Codex keeps absolute paths to this folder in its state database, and a thread resumed in a copy writes to the old folder's thread file, so the copy clears each chat's thread and the AI starts afresh with the saved chat, as after a model change (ADR 0004). A link or special file stops the move by name. The check: the database passes `checkDatabase`, every original it names is there, and every other copied file has the source's SHA-256. The Keychain entry is under `chatgpt.json`'s host id, not the path, so the moved folder stays signed in.

A failure the command sees before the switch cancels the move itself. A crash leaves a state that a start refuses and that `--finish` or `--cancel` ends, both under the same locks: `--finish` checks the copy again (never trusting an earlier check) and commits; `--cancel` marks the new folder cancelled for good, then clears the source's marks, keeping every file of both. After the switch, the location file names the new folder, which has no mark, so both are refused with "no move". The old folder is never deleted by Rufi.

| Source            | New folder                  | Location file | A start opens                    |
| ----------------- | --------------------------- | ------------- | -------------------------------- |
| `moving-out.json` | `moving-in.json`            | source        | neither                          |
| `moving-out.json` | complete                    | source        | the new folder, with `RUFI_HOME` |
| `moved-to.json`   | complete                    | source        | the new folder, with `RUFI_HOME` |
| `moved-to.json`   | complete                    | new folder    | the new folder                   |
| none              | `moving-in.json`, cancelled | source        | the source                       |

The desktop shell doesn't resolve the folder: it reads no server code and no file. It keys its Chromium profile (and so its one-app-per-folder lock) on `RUFI_HOME` when set, else on the remembered folder as a whole, and `rufi start` resolves the folder itself and tells Settings how it was chosen (default, moved or `RUFI_HOME`). Tests never reach the person's folder: vitest gives every test a scratch `HOME` (`tests/scratch-home.ts`), the resolver takes the home folder as a parameter, and the Electron fixture runs each app with a scratch `HOME`.

Considered: `~/Library/Application Support/Rufi` (the Mac's place for app data, but Rufi's home is meant to be easy to find in the terminal and to grow with skills and customizations); an editable path in Settings (one typo starts an empty record); following `RUFI_HOME` forever (every start needs the terminal); moving by rename (impossible across disks, and no point to check); copying `codex/` (proven to write into the old folder on resume); a pending move in the location file (invisible to a `RUFI_HOME` start); adopting an existing folder (`use-data`), deferred. The cost: a move copies the whole folder and reads every file twice; the AI's own history of the chat stays behind; a crash between the new folder's completion and the switch leaves a folder that `RUFI_HOME` can open and `--cancel` then retires; an older Rufi doesn't know the marks.
