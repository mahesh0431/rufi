# 0036 · Paired apps reach the remote door by one route of three

**Date:** 12 Nov 2026 · **Status:** accepted · amends [0032](0032-paired-apps-reach-rufi-through-the-remote-door.md)

ADR 0032 gave the remote door one way in: Tailscale Serve, on the tailnet only, never Funnel. Tailscale needs a VPN on the phone, and many phones can't or may not run one (a work iPhone, for one). So the door gets a **route**, chosen in Settings › iPhone: **Tailscale** (Serve, the start), **Tailscale Funnel**, or **Cloudflare Tunnel**. Whether the door is public is the person's choice; Settings says once, plainly, that a public route is public.

**A route is a small seam** (`server/remote-route.ts`): `up` at a pairing gives the door's Host and sets the route up, `resume` at a start brings back what doesn't outlive Rufi, `down` when nothing needs the door removes only what `up` set, `close` at quit ends what can't outlive Rufi. The record's `remote.route` names the route in use. Everything 0032 says of the door stays: the exact Host and Origin, the routes' classes, keys for one person, a code that works once. The door's own check moves out of Tailscale: after `up`, it POSTs a code that can't work to `https://<host>` and only Rufi's own 410 passes; while what answers isn't Rufi (no connection yet, a route's own error page), it asks again every 2 seconds, up to 30.

**One route at a time, changed only while nothing is paired** and no code is live or being used, on the server. A phone keeps the address it paired at, so changing the route means pairing again. Each route keeps its address while anything uses the door, so pairing a second phone never moves the first.

**Funnel's port is Rufi's own.** Funnel listens only on 443, 8443 and 10000, and shares one configuration with Serve, the latest command on a port winning. Rufi reads `tailscale funnel status --json`, takes the first of 8443, 10000, 443 that nothing holds (a command in the foreground too), saves it in `remote.funnel`, and reuses it for every pairing and after restarts. It moves only when no app is paired; with one paired and its port taken by something else, Rufi says so instead. `down` turns off that port only while it is still Rufi's own. HTTPS ends on the Mac: Tailscale's relay passes the traffic without reading it.

**Cloudflare Tunnel is set up with an API token,** not cloudflared's browser login. The login's file can manage every tunnel in the account, and when its transfer fails (a slow sign-in is enough) the browser downloads it to the person's Downloads folder, which Rufi can neither keep from Rufi AI's commands nor clean up. So the person makes a token on Cloudflare's own form (Cloudflare Tunnel: Edit; Zone: Read; DNS: Edit) and pastes it with the address, in Settings › iPhone. Rufi uses it for that call only: it finds the address's domain (the zone whose name is the longest end of the address), makes a tunnel of its own (`rufi-<random>`, its routing local, a secret of 32 random bytes) or reuses the one it made in that account before, and adds a proxied CNAME from the address to the tunnel. It never replaces a record: Cloudflare refuses to add one beside another, and Rufi shows its words. It writes each tunnel's credentials itself, in cloudflared's file format, in a file of their own, and the address and its tunnel last, as the commit; a setup cut short, also one in another account, leaves the address set up before, and its tunnel, as they were. Setup runs only while nothing needs the door, and pairing or choosing the route wait for it to finish (they are refused meanwhile). The token stays valid in Cloudflare until the person deletes it there.

**Cloudflare's secrets stay in the data folder's `cloudflare/`:** the tunnel's credentials (for this user only), the address, and the `config.yml` Rufi writes at each start of cloudflared: the address to the door's port, everything else 404. Rufi AI's commands can't read the folder, and Rufi's backups don't hold it; a restore elsewhere sets Cloudflare up again, with a new tunnel, so two Macs never share one tunnel's secret. cloudflared runs as Rufi's child (`cloudflared tunnel --no-autoupdate --config <file> run`), with only file paths in its arguments and only `PATH` and its own `HOME` in its environment, so it never reads the person's `~/.cloudflared`. It runs under the same watcher as Claude's process, so it ends when Rufi ends, a crash too, and no tunnel outlives the door; `down` and `close` stop it, and `resume` starts it again. If it stops by itself, Settings says so, and Rufi's next start runs it again. HTTPS ends at Cloudflare, which passes the traffic on through the tunnel; the request's Host stays the address, so the door's exact Host check holds.

The reason: people whose phones can't run a VPN can use Rufi on them, with nothing built for one route only, and the door's protections unchanged. The cost: on a public route anyone on the internet can reach the door's address and its public files (Rufi's screens, no health data); only a live code or a paired app's key opens anything else. Rejected: two routes at once (each phone would need to know both, and the door two Hosts); a bulk unpair when the route changes (the person unpairs, which they see); cloudflared's browser login (above); a tunnel token from Cloudflare's dashboard (more steps by hand, and its routing lives in the dashboard); a launchd service for cloudflared (it would outlive Rufi and the door); quick tunnels (a new random address at each start); Server-Sent Events for the chat's stream, while cloudflared passes `application/x-ndjson` on as it is written.
