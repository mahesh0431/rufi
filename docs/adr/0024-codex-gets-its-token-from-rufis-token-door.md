# 0024 · Codex gets its ChatGPT token from Rufi's token door

**Date:** 30 Oct 2026 · **Status:** accepted · **Pin:** `@openai/codex` 0.163.0

A reply has no time limit. Codex ran with a fixed `ACCESS_TOKEN` in its environment (ADR 0001), so Rufi gave it a token that outlasted a whole turn, cut a turn at 5 minutes, and replaced app-server between replies when the token changed. And on macOS any program of the user's, the AI's sandboxed commands too, can read another process's arguments and environment (`sysctl` `KERN_PROCARGS2`): the token in Codex's environment was readable by the AI.

**Decision.** Rufi's ChatGPT-plan provider has no `env_key`. Its token comes from Codex's provider auth command (`[model_providers.openai_chatgpt_plan.auth]`: `command`, `args`, `timeout_ms`, `refresh_interval_ms`). Each app-server has its own **token door** (`agent/codex/token-door.ts`): a loopback HTTP endpoint with a new random key, opened before app-server starts and closed when it ends. Its address and key are in `codex-door/door.json` beside the Codex home, readable only by the user, and the AI's sandbox denies the whole `codex-door/` folder (the file's temporary copy too), the chat's and the reader's. Codex runs `node token-command.ts <that file>` with Rufi's own node, outside the sandbox. The command reads the file and asks the door, which checks the key on every request and answers with Rufi's token, valid for 2 minutes at least. Codex asks again once its token is a minute old, and after OpenAI refuses one (a 401). Nothing secret is in Codex's arguments, environment or settings: `config.toml` names only the command and the file.

- **No time limit and no token lifetime rule.** A turn runs until it ends or Stop; app-server is never replaced for a new token. The reader keeps its own deadline (ADR 0009).
- **Signed out during a turn.** Codex fails a turn it got no token for with only the command's words, so the door remembers when it had none because Rufi is signed out, and that turn ends signed out. A 401 after Codex asked the door again ends the turn signed out too. The input stays delivered and isn't sent again.
- **The 2-minute ask.** ChatGPT renews a token only from its `earliest_refresh_at`. A longer ask can fall in the gap before it, when Rufi has no token to give.
- **What Codex does, probed live on a test sign-in.** It runs the command as app-server starts, whenever its token is older than the refresh interval (mid-turn too), and after a 401, then retries. A failing or hanging command is run again with each of 5 reconnects; then the turn fails. The command is killed at `timeout_ms`, and has its own deadline under it.
- **Pinned.** The auth command isn't on OpenAI's pages, so `contract.test.ts` fails if the pinned Codex stops asking the door again after a 401. The macOS canary (`capture.test.ts`) reads Rufi's own process and app-server from inside the AI's sandbox, as the AI could, and fails if either holds the token, an MCP key or the door's key.

Considered: Codex's external-token login (`account/login/start` with `chatgptAuthTokens`, renewed through `account/chatgptAuthTokens/refresh`), which refused Rufi's Sign in with ChatGPT token ("workspace routing discovery unauthorized"); the door's key in Codex's environment or in the command's arguments, both readable by the AI as above; a token that outlasts a turn, with a cap on the turn.

The cost: the auth command is undocumented, so each pin bump reruns the contract tests and the live probe (`scripts/codex-auth-probe.ts`). A node process starts each time Codex asks, about once a minute while it works. A door that never answers costs Codex's whole retry run before the turn fails.
