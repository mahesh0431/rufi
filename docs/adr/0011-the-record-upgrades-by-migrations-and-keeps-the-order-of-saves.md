# 0011 · The record upgrades by migrations at start, and keeps the order of saves

**Date:** 11 Oct 2026, retiring a kind 24 Oct 2026 · **Status:** accepted

From dogfood on, the record holds real data, so a new Rufi can no longer ask for it to be reset. The record's version is SQLite's `PRAGMA user_version`. Version n is what migrations 1 to n make (`core/store/migrations/`, plain SQL, listed in order in `migrations.ts`); `schema.sql` is the last version, with its `user_version` set, and a test checks that the migrations make exactly it. Migration 1 is the record as Rufi made it before it had versions. Such a record has `user_version` 0 and is known only by its exact shape (its tables and indexes, without comments, quotes or spacing); any other unversioned database is refused, never taken as new. A migration that shipped never changes; a change is a new one at the end. Rufi decides at start, in `openRecord`, while it holds `rufi.lock`, before anything else opens the record: it reads the version and shape through a read-only connection, so a record from a newer Rufi, or one it doesn't know, is refused and left exactly as it was (no journal-mode change first). An older record is backed up first, with the same checked backup as every day, into `backups/before-upgrade`, which pruning never touches, since the next start's backup would otherwise replace it the same day; a backup that fails stops the upgrade. After that check, the upgrade uses WAL before it writes, so a crash leaves the old record readable at the next start without a writable connection recovering a rollback journal. Then every pending migration and the new version run in one transaction, with foreign keys off (a migration may rebuild a table), and commit only when `integrity_check` and `foreign_key_check` pass; any failure rolls all of it back, so a crash or a bad migration leaves the old record. Backups of an older version still count: checking one reads its version and runs SQLite's checks without changing it. A restore upgrades only the copy in the new folder, before it holds that copy's queue, and never the backup. The order of saves is `operations.seq`, 1, 2, 3 across people, set by the save in its own transaction (the next after the highest; the save holds the write lock), and backfilled by migration 2 from the order the rows were stored in. Every reader of history order uses it: a record's version, a brief's values and sources, and the latest saves. Time can't order saves (the Mac's clock can move back), and rowid can't either (a `VACUUM` may renumber rows of a table without an integer primary key). A person's record version stays the count of their saves. Considered: one transaction per migration (a failure in the second would leave a half-upgraded record); a backup only of the newest version (the backup before an upgrade would fail on the record it protects); keeping rowid with a note never to `VACUUM` (a rule nobody enforces). The cost: an upgrade on a large record copies and checks it before Rufi opens, the backups before upgrades stay until the person deletes them, and a migration can only be written in SQL until one needs code.

**24 Oct 2026: retiring a kind.** A kind of record can go at an upgrade (migration 15 drops prescriptions and the care event type visit, ADR 0021). Its rows are named by kind and id in places a foreign key doesn't check (history, sources, a follow-up's about, a brief's citations), and the readers expect every kind they meet to exist. So the migration retires each reference before it drops the rows: their history and sources go, a follow-up about one is about nothing (in its history too, so an old change's reverse names no gone record), and a brief keeps its words but no longer cites them. A save's receipt stays in the chat as written, and its other changes stay. The backup made before the upgrade keeps them all.
