# 0010 · The reader runs on GPT-6.1-Sol, with Codex's exec in its pinned set of tools

**Date:** 11 Oct 2026 · **Status:** accepted

Documents are read with GPT-6.1-Sol at Medium effort by default; GPT-5.5 stays as the other choice in Settings, and a stored choice of either is kept. On the pinned Codex every GPT-6.x model is code-mode only: the model gets Rufi's tools only inside Codex's `exec` tool, which runs JavaScript in a V8 isolate with no Node, no file system and no network, and Codex always adds `exec`, `wait` and `request_user_input_async` beside it and `clock__curr_time` inside it, with no setting to turn them off. So the runner (`agent/codex/subagent.ts`) names each model's route (`SUB_AGENT_MODELS`): direct for gpt-5.5, code for gpt-6.1-sol, and the thread settings stay the same for both (plus Codex's sleep tool off). The allowed set on the code route is pinned exactly: at the top `exec`, `wait` and `request_user_input_async`; inside `exec` only `rufi__get_page`, `rufi__save_page` and `clock__curr_time`. `subagent.test.ts` proves this set on the real pinned Codex in every request, also after a forced compaction, and that a page image reaches the model through `exec` (the script passes the page's data URL to `image()`); a test that adds a tool, a namespace, sub-agents or the sleep tool goes red. At run time a call through `exec` is allowed only on the code route; on the direct route it still fails the turn, and a question to the user (`request_user_input_async`, shown as an agent message with questions) fails the turn on either route, because the reader has nobody to answer: the attempt's entries make no drafts, as for any other failed turn. The reason: the person chose Sol for reading quality, and accepted these extras; none of them reaches files, commands, the network, other agents or the record, and the reader's two tools are still bound by code to one person, document and attempt. The cost: about ten times the tokens. On the reader pack's small dense set (11 Oct 2026), both models read every item right (110 of 110, PDF and photos), Sol at Medium in 17–24 s a page and GPT-5.5 at Low in 26–28 s, but Sol used about 111k tokens a page (about 77% cached) against about 10.5k: its first request already carries Codex's `exec` description, and the whole context goes again with each request. The reader's contract is wider than two tools and depends on a pinned Codex detail (the `exec-` call ids and the exposed set), so a Codex upgrade must pass `subagent.test.ts` again; an image reaches the model only when its script shows it, which the reader pack measures, not code. Considered: a custom model catalog or a Codex fork to remove the extras (more upkeep, with no evidence it reads better); staying on GPT-5.5 only (the person chose Sol for reading).

**Amendment, 14 Oct 2026: the reader's tools over MCP (ADR 0016).** The reader's two tools now come from Rufi's MCP endpoint for the reader (`/mcp/reader`), as the server `rufi`, with a key for one reading attempt, bound to one person, one document and one attempt. The key opens nothing from the moment a Stop, a cancel, a delete or a newer retry begins, nor after the attempt ends, and a chat's key opens nothing there. Every lock on the reader stays as it was. The tools are eager (`omit_tools_from: ["deferred"]`), so neither model has to search for them: deferred, GPT-5.5 would get Codex's `tool_search` beside them. Codex adds its three MCP resource helpers for any MCP server, with no setting to turn them off; they find nothing, because the endpoint offers no resources. So the pinned set is now: on the code route, at the top `exec`, `wait` and `request_user_input_async`; inside `exec` `mcp__rufi__get_page`, `mcp__rufi__save_page`, `clock__curr_time`, `list_mcp_resources`, `list_mcp_resource_templates` and `read_mcp_resource`. On the direct route: the namespace `mcp__rufi` with `get_page` and `save_page`, and the three helpers. `subagent.test.ts` proves both sets on the real pinned Codex, also after a compaction, with the server's id. A page comes back as MCP image content; on the code route it reaches the model only when the script passes that block to `image(...)`, which `subagent.test.ts` proves. The run-time rules are the same, with the helpers allowed: a call to one of the two tools or a helper is the only item allowed, and on the direct route a call through `exec` still fails the turn. One difference: Rufi can't stop a call Codex makes to its MCP server, so on the direct route such a call reaches the tool before the turn fails (GPT-5.5 has no `exec`, so this doesn't happen in practice).

**Amendment, 14 Oct 2026: the reader keeps Codex's prompt (ADR 0016).** The reader's instructions are now its developer instructions, after Codex's own prompt with the personality `none`; before, they replaced that prompt. Every other lock and the pinned set stay as they are. The reader's version names this (`prompt` in `READER_VERSION`). `subagent.test.ts` checks the prompt, the instructions and no other message before the task. The reader pack measures the reading quality.

**Amendment, 24 Oct 2026: Codex 0.163.0.** Codex now honours the reader's `request_user_input` setting for `request_user_input_async` too (openai/codex#51908), so the pinned set on the code route is `exec` and `wait` at the top; inside `exec` it is unchanged. A call to the question tool gets "unsupported call" and reaches no one. Rufi still fails the turn if an agent message carries questions. Codex now sends its own prompt as the first developer message on both routes, not in `instructions`; the content is the same, and `subagent.test.ts` checks it there. Every other lock stays as it is.
