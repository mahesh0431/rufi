# 0030 · Rufi AI's reply is OpenUI Lang

**Date:** 1 Nov 2026 · **Status:** accepted · Supersedes [ADR 0029](0029-a-replys-trend-is-drawn-by-rufi-from-the-ais-block.md)'s trend block in a Markdown reply, and [ADR 0017](0017-a-reply-shows-the-files-the-ai-made.md)'s pages and diagrams

Every reply of Rufi AI is OpenUI Lang, drawn by OpenUI's renderer in place of the Markdown renderer, as it is written. As in OpenUI's own chat, the renderer gets the whole reply so far on each change and draws each part as it parses; both providers stream the reply's text (Codex's `item/agentMessage/delta`, Claude's `text_delta`), so it builds part by part. This follows OpenUI's recommended path for a chat UI of one's own: the agent writes OpenUI Lang, and "adding OpenUI changes a single component". Mahesh asked for OpenUI for the whole reply, so Rufi doesn't build its own kit. Rufi's chat stays: Activity, receipts, the waiting list, the box and the dog. Notes, an agent's messages, receipts and visit briefs stay Markdown.

**OpenUI's parts only.** The library is `openuiChatLibrary` from `@openuidev/react-ui` 0.18.1 (pinned, with `@openuidev/react-lang` 1.0.2), with no part of Rufi's own (`apps/web/src/openui/library.ts`). With `library.extend`, Rufi draws some of them, with the same names and props: `TextContent`, `MarkDownRenderer`, `Callout`, `Steps` and `Card`, so every link opens by Rufi's rule, and `Image`, for a picture file. The rest are drawn as OpenUI draws them.

- **One test over time is one of OpenUI's charts**, like any other numbers, though its `LineChart` spaces points evenly and draws a missing value at 0. Mahesh chose this over Rufi's own trend part. Rufi's data rule stays in the prompt: every value comes from the record or a document as it is kept there, never invented or rounded, and a value a chart can't take as a number, such as "<5", stays as printed in the text or a table. OpenUI's chart labels and hover round numbers (0.0025 shows as 0.003, 123456 as 123.4K), so the rule and the prompt's example show a chart of health values with its values as kept, in a table or the text: the chart is the picture, the table has the exact values. OpenUI's formatter isn't patched. The test's own chart, spaced by date, stays on its page in the record, and Rufi AI can link it (`rufi:/tests/<id>`, in the core instruction's list of Rufi's addresses).
- **No page and no diagram.** A summary for a doctor is an ordinary reply, and the visit brief stays as it is; a process shows with OpenUI's `Steps`, as its guide says. So Rufi no longer serves an HTML file the AI made, and has no page or diagram frame, route or policy: the screens' `frame-src` is `blob:` only (a document's original), and the app sends a web link to the browser only while the window has no frame. Rufi paper (`paper.css`) went with the page, and with it a skill's files beside its SKILL.md: a skill is its SKILL.md.
- **A stored reply with a part the library no longer has** (`Trend`, `Page`, `Diagram`) shows as its text, as any part the library doesn't know does. Nobody uses Rufi yet, so there is no migration.

**The prompt is OpenUI's, from the same library.** `pnpm openui:md` writes `core/chat/openui.md` with `library.prompt(...)`, and a test checks the committed copy. Rufi AI gets it after its core instructions; an agent it starts doesn't, and writes Markdown. It is about 56 KB, given once per thread and cached.

- The options are the chat library's, with a Rufi preamble in place of OpenUI's default, and Rufi's rules added: values only from the record as it keeps them, links to Rufi's pages, pictures as files in the AI's folder, and what buttons send.
- OpenUI's chat rule "When asked about data, generate realistic/plausible data" is left out: Rufi never invents health data. The script stops if that rule is gone, so an OpenUI upgrade is checked.
- Rufi's core instruction asks only that each reply is easy and pleasant to read, with the parts that fit it, and leaves the how to OpenUI's guide.
- No inline or edit mode, and no tools: a reply is a whole program each time, with no `Query`, `Mutation` or bindings.
- OpenUI's CLI would write the same prompt, but it bundles with esbuild and sends telemetry. The library is written without JSX, so Node loads it directly.

**A finished reply with a piece left out draws the rest and says so.** OpenUI drops what it can't resolve, validate or draw, sometimes without an error: it doesn't check which part sits in a part's place (a `TextContent` where a `Table` takes a `Col` draws as an empty column), it draws nothing for an object in a table cell, and it passes over words outside its statements. So a health value could vanish from the screen. One rule, one way: whatever of the text isn't surely drawn makes the reply partly shown; a notice too many is fine, a value left out without one isn't. Once a reply ended, it is whole only when:

- OpenUI's parse is whole: nothing cut off, nothing unresolved or orphaned, no errors at all;
- OpenUI took in all of its text, read with its own tokenizer and parser: each piece is in a statement, each statement is one expression all through (nothing after it that the parser passes over), no name is given twice, no comment, and each string and number in the text is in the tree it made, as many times as the text has it;
- its tree fits the JSON schema OpenUI makes of the library, from its `Card` down: each part only where that part may go (anywhere in a place the schema leaves free, such as a table column's data), each part's props by its own schema wherever it sits, each prop by its type, nothing coerced, and a free place holds only values, parts and lists of them. An expression OpenUI keeps, such as an action, known by its kind, is OpenUI's to read;
- and drawing it raised no error (the renderer's `onError`).

  Otherwise OpenUI draws it as it draws any reply, what it can't draw left out and the rest shown, with "Part of this reply couldn't be shown." and **Show text**, which opens the reply as written, so no value is hidden. While a reply is written, a piece not there yet is normal: the check runs once the AI gave the reply whole (its entry is `done`), also while its turn goes on. A reply with no OpenUI in it shows as Markdown, so a reply is never blank. Rufi first showed such a reply only as its text; most of a reply was lost to one broken piece, and asking again cost a whole turn.

**Styles follow OpenUI's Tailwind v4 recipe, without its ThemeProvider.** `styles.css` declares `@layer theme, base, openui, components, utilities;` and imports OpenUI's layered stylesheet. OpenUI's `ThemeProvider` writes colours into a `<style>` element, which the screens' CSP (`style-src 'self'`) refuses. The stylesheet itself holds OpenUI's light and dark tokens, chosen by `data-openui-theme` on the page, which `theme.js` sets with Rufi's theme before the first paint. OpenUI's chat components keep their own copy of its theme context, so a mode passed from outside wouldn't reach them anyway. Zod is set `jitless` as the screens' first import, before OpenUI builds its schemas, so the CSP refuses nothing. OpenUI's typography tokens (fonts, sizes, weights, font variation and tracking, which its theme sets for Inter) are set in `styles.css` to Rufi's chat text: the UI font, 13 px body, regular 400 and medium 500, headings semibold, normal tracking, the same in light and dark. So a reply reads like the messages and Activity around it.

**Actions as OpenUI says.** A follow-up or a button (`continue_conversation`) sends a message of its own, as OpenUI's guide to user actions does: the chat shows its words (`humanFriendlyMessage`) as the person's message, and Rufi AI gets `User clicked:` with them, a form's values (`Form values:`) and the context its action carries (`Context:`, which card or item was clicked, as OpenUI's own chat keeps it). The message keeps both (`ai_text` beside `text` in `chat_queue` and `transcript_entries`); what Rufi AI reads back of the chat (`read_chat`, a new thread's last messages) is what it got. A click isn't the box's: what the person typed and hasn't sent stays there. An edit of a waiting click sends the edited words as written. An `open_url` opens as a link in a reply's text does: Rufi's own `rufi:/…` link opens the person's page in place, and a web address opens outside Rufi.

**The parts Rufi draws:**

- **TextContent, MarkDownRenderer, Callout and Steps.** OpenUI's Markdown component, given Rufi's reply link parts through its `options`; `TextContent` keeps OpenUI's `[n]` citations of the Card's sources. OpenUI's Markdown component opens every link in a new tab, and OpenUI's `Callout` and `Steps` use it directly, so they are drawn as OpenUI draws them with Rufi's Markdown.
- **Card.** OpenUI's chat Card, whose sources and citations open by Rufi's rule: OpenUI's own call `window.open`. Their favicons aren't fetched; Rufi's screens load nothing from the web.
- **Other links OpenUI draws itself**, such as an `EditableTable`'s address cells, keep their raw address and stop their click. The reply catches such a click first (a capture handler) and opens it by the rule: a `rufi:/…` address in place; anything that isn't a web page or Rufi's own does nothing.
- **Image.** A picture file from the AI's folder by its path. Rufi's screens load no web pictures, so a web address shows as its words. A picture the AI generated shows once when the reply shows it, by `Image` or in its Markdown text.

**Display only.** No `toolProvider` and no tools in the prompt, so nothing in a reply reaches the record. Every string is text.

**Replies are kept as written.** A part Rufi draws keeps OpenUI's name and props, and an old reply that no longer fits the library shows as its text. Replies written before this one are Markdown, and still show as Markdown.

**Considered:** OpenUI's `AgentInterface` (a second chat, where Rufi already has its own); inline mode (text with fenced blocks, which is ADR 0029's shape, and not the recommended path); `LineChart` for results over time (it misplaces dates); OpenUI Gateway or Autofix (a cloud service between Rufi and its providers). **Not now:** saving a form's values across reloads, OpenUI's artifacts panel, and a tuned type scale (OpenUI's text is its own size, a little larger than Rufi's chat text).
