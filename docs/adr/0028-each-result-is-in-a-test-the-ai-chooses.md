# 0028 · Each result is in a test the AI chooses

**Date:** 1 Nov 2026 · **Status:** accepted

Two labs name one test differently ("S. Creatinine", "Creatinine, serum", "CREA"), print it in different units (mg/dL, µmol/L) and with their own ranges, so the values of one test never met: a test's line was its exact printed name and unit. Now each person has a list of their **tests** (the `tests` table, the record kind `test`): a name, a section and the unit its numbers are in, all in the AI's words. Every result points at one (`results.test_id`, required, a composite `(person_id, test_id)` foreign key, so a result is only ever in its own person's test). Results keep everything as printed; what is added beside it is the AI's: which test, and the result's numbers in the test's unit (`test_number`, `test_second_number`): the printed number when the units mean the same (mg/dl and mg/dL), converted when they don't and the AI knows how for that substance (97 µmol/L of creatinine is 1.1 mg/dL), none when it can't compare.

**The AI chooses, when it saves, and code never reads the words.** A result's test, a test's name, section and unit, and the numbers in the test's unit are judgement, so they are the AI's with the user, as the category is (ADR 0013): its skills say how to tell one test from another (the same thing measured in the same kind of sample, whatever the lab calls it or its method; another sample, a share against a count, a timing that is part of the test or a value worked out from another make another test) and how to convert, and to ask when it isn't sure. Code groups by the stored id and never compares names or units, or checks the AI's arithmetic. A save can add a test and the results in it at once: the test's add gives a `ref`, which a result's `in_test` names, as a visit's ref is cited. An amended result keeps the test of the one it replaces unless the save gives another; its numbers are its own. A result read from a document changes its test and numbers in place, like its category, since none of them is printed; what it prints and its date still change only by amendment (ADR 0005).

**Joining, splitting and renaming are ordinary saves.** A rename or a new section is a change of the test. A join or a split moves each result to another test with its numbers in that test's unit, in the same change; its undo sets both back. A test is never removed (`kept`): one with no current results stays, and the AI can reuse it; so an undo of a save that added a test leaves the test. `get_records` lists a person's tests with what their current results printed (names and units) and how many there are, so the AI picks one without reading every result, and reads one test's results with `test`.

**Lab results lists tests, not reports** (superseding ADR 0013's "Lab results group by report"). Each of the person's tests with a current lab result shows once, under its section (sections and tests in name order, case-insensitive, no section last), with its latest lab result as printed and how many there are. Latest is by sample date, then the later saved, so an older report saved today isn't latest; an undated value counts only when the test has no dated one. The whole list loads at once, with no paging: a person has tens to a couple of hundred tests. A test has its own page (`/people/<id>/tests/<test>`) with every current value, newest first, its report's lab, and its numbers in the test's unit when they differ from the printed ones; a link to a lab result opens it there. The report itself stays whole on its document's page. The Lab results tile and the sidebar count tests; the tile's latest line is still the latest report, so the read model keeps its report groups for it. Measurements is unchanged.

**One line across labs** (superseding ADR 0013's "a lab test and a measurement of the same name are two series"). A test's line is every current result of the test, whatever its page, printed name or unit, at its `test_number` (and `test_second_number`, dashed) by sample date; one with no number in the test's unit or no calendar date isn't on it, and the test's list says so. Its labels and spoken words come from those numbers, in the test's unit, or as printed when they are the printed numbers; the comparator comes from its own field, and nothing reads `value_text`. The newest range is written as printed, with that value's printed unit and its lab. The small trends on Lab results and Measurements, and a measurement's open row, draw the same line; the series by printed name, unit and category goes.

**Results saved before tests** get one test for each person, printed name, category and printed unit, named as printed, with that unit and no section, their numbers copied (migration 28). That is how Rufi joined them before: a compatibility value from before real data existed, not a judgement. The same name in two units is two tests until the person asks to join them. The unused `group_label` goes.

**Considered:** a shared label on each result (the column `group_label`, never used): the smallest change, but a test's name repeats on every value, so a rename changes them all and a slip silently starts another test, and a test's unit has no place to live; LOINC codes as the identity (codes split creatinine in mg/dL from creatinine in µmol/L, professional mappings are about 4–5% wrong and an AI's from memory far more, and a code is something the person can't check); a test list shipped with Rufi with conversion factors (a medical content job of its own); grouping when the page loads by matching names in code (code reading people's words). **The cost:** every save of a result names a test, and of a result with a number, its number in the test's unit; a long first report makes many tests in one save; a conversion is only as good as the AI's, so the table shows each value as printed beside it; after a test's unit changes, a result removed earlier keeps its old number and brings it back if it is put back, until the AI changes it (a TODO).
