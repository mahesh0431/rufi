# 0018 · The AI keeps its thread: new rules as a note, a new thread only when it is gone

**Date:** 17 Oct 2026 · **Status:** accepted

The chat's AI keeps one Codex thread for as long as it can, and the chat says honestly what happened to it. Before, Rufi showed one line for a new thread and for Codex's compaction, started a new thread on any error while it opened the saved one, and compacted the thread itself whenever Rufi's rules changed.

**New rules reach the thread as a note, not a compaction.** A loaded thread ignores new settings, and its history keeps the developer instructions it was first given (0.159.3). When the rules version changes, Rufi lets the thread go, resumes it with the new core (what Codex starts from again after it compacts), and adds the complete new rules to its history as one developer message with `thread/inject_items`, saying they replace the earlier ones and that a skill is read again before use. Since Rufi AI runs on the agent package (30 Oct 2026), Codex's adapter adds that message (`instructionsNote`) at every resume, as it keeps nothing between opens, so a restart with the same rules gives them again too. The stored version means "the thread's history has the current rules": it is written only after Codex answered the injection, which it stores before it answers. A Stop, a refusal or a crash before then leaves the old version, so the next hand-over gives the rules again; a repeated note does no harm, a repeated user message would. `capture.test.ts` proves on the pinned Codex with its fake model that the complete rules reach the next request, a cold resume and the request after an automatic compaction (from the resumed core: the note itself is not kept by the compaction), for a region change and a skill-only change, and again after an update that didn't reach the AI. Rejected: `turn/start.additionalContext` (each value is cut to about 1,000 tokens, and the core is about 5 KB); keeping the forced compaction (slow, and a failure held the message).

**A new thread only when the thread is gone, or by choice.** Rufi starts a new thread when the chat has none (the first message, a move, the person's **New thread**), when the thread is another agent's, or when Codex answers the resume with JSON-RPC `-32600` and exactly "no rollout found for thread id <id>" for that id: the one check of a Codex error, at the resume boundary only (the dispatcher's resume, the rules reload, and the reopen in `send` after a new sign-in replaced Codex). Any other failure to open the thread (a read error, a settings check, the rules not taken) is not proof of loss: the person's message waits with Codex's error, and the person chooses **Try again** or **New thread**. Rejected: matching every `-32600` or "not found" text; retrying by itself.

**One held error, one choice.** Such a hold is its own state (`held = 'open_failed'`) with an id for that occurrence (`hold_id`). Try again and New thread name it; one transaction in the chat's operation lane checks it is still the current one, clears it, puts the message first and ends the pause, and for New thread also clears the chat's thread. A click on an older hold, or a second tab's click, changes nothing and the screen reads the queue again. A Try again that fails again makes a new hold. A message that is "not sure" never gets these choices, so New thread is never a resend of a message the AI may have.

**The meter.** The chat keeps the last `thread/tokenUsage/updated` it heard (`last.totalTokens`, `modelContextWindow`) and the thread it was for; the screen shows `last / window` as a rounded percentage only while that thread is the chat's and the window is known. It is read also outside a reply (a resume replays it). A new thread shows nothing until it reports.

The cost: the injected note grows the thread's history by the core's size at each rules change, and Rufi now depends on two more pinned Codex details (`thread/inject_items`, the not-found message), which `capture.test.ts` and `chat.test.ts` check on the real binary.

**30 Oct 2026: no pause (ADR 0004).** Try again and New thread put the message first; there is no pause to end. The agent package opens the thread again, and a held message goes once nothing runs.

**31 Oct 2026:** Try again is the failed message's **Send** (ADR 0004); New thread stays, and only this hold has it.
