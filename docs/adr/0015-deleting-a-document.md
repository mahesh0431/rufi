# 0015 · Deleting a document

**Date:** 11 Oct 2026 · **Status:** accepted

A document added by mistake (someone else's report, a blurred copy) must be removable from Rufi, not only hidden: its original, the pages drawn from it, the reader's work, its readings and its draft items. A document and its draft items aren't the record (ADR 0005), so deleting one is a screen action, like adding one: **Delete** on its page, a preview, a confirm. There is no AI tool; the AI can't delete.

**The person chooses what becomes of saved results.** The record still changes only by a save in the chat. The preview lists the records that aren't removed (current, or replaced by an amendment, which comes back if that one is removed) and rest on a page of the document by a source no save took off. With such records, the confirm carries the person's choice, with no default, and a confirm without one is refused: **Delete file** (`keep`) deletes the document and keeps them, valid, their sources saying "document deleted"; **Delete file and results** (`remove`) deletes the document, opens the chat in that tab, and the AI goes through them with the person, removing each on a yes (`remove`) or taking this document off one the person also gave another way (`remove_source`, every page of it). Which of the two is the AI's call with the person, not code's. A Rufi note is never consent: the AI's own turn on it can only read, and the removals come in the person's turns. The delete doesn't wait for them: if the person stops halfway, the file is gone and the records not handled stay, as with **Delete file**. Undo brings back a removed record, never a page taken off or the file.

**A tombstone, not a purge.** The document's row and its pages' rows stay, with `documents.deleted_at`, the pages' names and positions, and no file (`document_pages.file_id` is null: migration 5). Reports, results, `record_sources`, operations and their history are untouched, so every foreign key holds and history, receipts, sources and briefs still read; they say "document deleted" instead of breaking. A tombstone is out of every list, count, Needs you, chip check and AI read, and every action on it is refused. Adding the same file again makes a new document: a tombstone's pages hold no file, so the duplicate check doesn't see them.

**One transaction, then the bytes.** The delete's database part is one transaction with its Rufi event in the chat ("Deleted …"): the draft items, the jobs and the reader's notes go, the chips of the document and of its draft items in sent and waiting messages are marked deleted (a draft item's chip names no document, so this is the last moment the link is known), its reading lines lose their link, and a `files` row goes when no live page of anyone uses it. The preview's version is a hash of what it shows (not a reading's progress); a delete made on another version is refused with the preview as it is now. The same transaction queues the event's note for the AI, naming the document and the person's choice: nothing saved came from it; or these records stay, valid; or the person asked to remove these records (each with its id, label and date). It goes like any Rufi note: at once in a turn of its own when nothing runs, after a running reply, and with the person's next message when the chat is paused (a Stop, a restart while it waited, signed out); it gives no consent to change the record. The AI's tools stop showing the document, and the line is in a new thread's earlier chat. The note, the AI's instructions, get_documents' refusal and a deleted chip all say the same: the document's pages are unavailable, so the AI doesn't use or quote what it read from them before; records saved from it are facts like any other until the person removes them, read through get_records, with the original said to be deleted.

**Readings stop for good.** The jobs go in the transaction, and the reader aborts its run when it reads this document. Every late path of a reading (the notebook's save, finish, fail, requeue, their chat lines) is guarded by the job's row, so a run that ends after the delete writes nothing and logs no failure; a restart has nothing to resume.

**The bytes under one gate.** Bytes are removed after the commit. One gate in memory (the core is one process under `rufi.lock`, `core/documents/gate.ts`) has two modes. Taken shared: a backup and the export, from their copy of the database through reading every original it names; an add, from writing its originals through its commit; keeping a drawn page or a display copy, which goes ahead only while its file has a `files` row. These don't get in each other's way: a backup's copy of the database just doesn't have a document added meanwhile, so a long backup holds up no reading and no add. Taken exclusive: the delete's removal, which waits for the shared work before it and removes an original and its caches only when no `files` row names it (an add of the same bytes meanwhile keeps them). Turns are taken in order, so a removal is never starved. Slow work, drawing a page or reading a file to send it, stays outside the gate. A backup or an export made beside a delete is whole: it names the file and has it, or names neither. If Rufi stops between the commit and the removal, the next start, before anything else, removes from `files/`, `cache/pages/` and `cache/display/` what no `files` row names, including half-written temporary files; names that aren't Rufi's stay. There is no cleanup table.

**What Rufi can't reach.** Backups never change: Rufi's own keep the document until they age out (about 5 weeks), and those made before an upgrade until the person removes them. Exports already saved, Time Machine and what the AI already read are outside Rufi. The preview and the help say so in plain words, and never that the data is erased everywhere.

Considered: deleting saved results with the document, in its transaction (a second way to change the record, against ADR 0005); refusing the delete while saved results rest on it (two trips for the person, and no way to keep right results without the file); a physical purge of the document's rows (history, sources and briefs would break, or need their own copies); a cancelled job state instead of deleting jobs (one more state for every read of jobs, for nothing to show); a durable cleanup table (the start sweep finds the same bytes from the `files` table alone); a fresh AI thread after a delete (it would lose the chat's context and still not erase what the AI read). The cost: a delete's removal waits for a backup that runs; a tombstone keeps the name of a file the person deleted; and the AI still has in its memory what it read in the current thread, which only its instructions keep it from using.
