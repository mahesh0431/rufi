# 0015 · Deleting a document

**Date:** 11 Oct 2026 · **Status:** accepted

A document added by mistake (someone else's report, a blurred copy) must be removable from Rufi, not only hidden: its original, the pages drawn from it, the reader's work, its readings and its draft items. A document and its draft items aren't the record (ADR 0005), so deleting one is a screen action, like adding one: **Delete** on its page, a preview, a confirm. There is no AI tool; the AI can't delete.

**Chat first for saved results.** The record still changes only by a save in the chat. While a record that isn't removed (current, or replaced by an amendment, which comes back if that one is removed) rests on a page of the document by a source no save took off, the delete is refused, and the preview lists those records. The person removes them, or takes the document off one that has another source (`remove_source`), in the chat; which of the two is the AI's call with the person, not code's. Removed records don't block. The check runs again inside the delete's transaction.

**A tombstone, not a purge.** The document's row and its pages' rows stay, with `documents.deleted_at`, the pages' names and positions, and no file (`document_pages.file_id` is null: migration 5). Reports, results, `record_sources`, operations and their history are untouched, so every foreign key holds and history, receipts, sources and briefs still read; they say "document deleted" instead of breaking. A tombstone is out of every list, count, Needs you, chip check and AI read, and every action on it is refused. Adding the same file again makes a new document: a tombstone's pages hold no file, so the duplicate check doesn't see them.

**One transaction, then the bytes.** The delete's database part is one transaction with its Rufi event in the chat ("Deleted …"): the draft items, the jobs and the reader's notes go, the chips of the document and of its draft items in sent and waiting messages are marked deleted (a draft item's chip names no document, so this is the last moment the link is known), its reading lines lose their link, and a `files` row goes when no live page of anyone uses it. The preview's version is a hash of what it shows (not a reading's progress); a delete made on another version, or with records that block, is refused with the preview as it is now. The event has no note for the AI: one would start a reply of its own. The AI's tools stop showing the document, and the line is in a new thread's earlier chat.

**Readings stop for good.** The jobs go in the transaction, and the reader aborts its run when it reads this document. Every late path of a reading (the notebook's save, finish, fail, requeue, their chat lines) is guarded by the job's row, so a run that ends after the delete writes nothing and logs no failure; a restart has nothing to resume.

**The bytes under one gate.** Bytes are removed after the commit. One gate in memory (the core is one process under `rufi.lock`, `core/documents/gate.ts`) is taken by: a backup and the export, from their copy of the database through reading every original it names; an add, from writing its originals through its commit; keeping a drawn page or a display copy, which goes ahead only while its file has a `files` row; and the delete's removal, which removes an original and its caches only when no `files` row names it (an add of the same bytes meanwhile keeps them). Slow work, drawing a page or reading a file to send it, stays outside the gate. A backup or an export made beside a delete is whole: it names the file and has it, or names neither. If Rufi stops between the commit and the removal, the next start, before anything else, removes from `files/`, `cache/pages/` and `cache/display/` what no `files` row names, including half-written temporary files; names that aren't Rufi's stay. There is no cleanup table.

**What Rufi can't reach.** Backups never change: Rufi's own keep the document until they age out (about 5 weeks), and those made before an upgrade until the person removes them. Exports already saved, Time Machine and what the AI already read are outside Rufi. The preview and the help say so in plain words, and never that the data is erased everywhere.

Considered: deleting saved results with the document (a second way to change the record, against ADR 0005); a physical purge of the document's rows (history, sources and briefs would break, or need their own copies); a cancelled job state instead of deleting jobs (one more state for every read of jobs, for nothing to show); a durable cleanup table (the start sweep finds the same bytes from the `files` table alone); a fresh AI thread after a delete (it would lose the chat's context and still not erase what the AI read). The cost: the gate makes a delete's removal and an add wait for a backup that runs; a tombstone keeps the name of a file the person deleted; and the AI may remember what it read in the current thread.
