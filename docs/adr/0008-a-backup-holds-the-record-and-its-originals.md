# 0008 · A backup holds the record and its originals, and Rufi never starts over without it

**Date:** 8 Oct 2026, originals added 10 Oct 2026 · **Status:** accepted

A backup is `rufi.sqlite` and every original document file it names: SQLite's online copy, made in one step (one read of the database, so a save is in it whole or not at all) into a new private staging folder in `backups/`, made a single file, checked (it opens as Rufi's schema, `integrity_check` and `foreign_key_check` pass, and its size and hash match its own `backup.json`); then each original that copy's `files` table names is copied from `files/` into the backup's `files/`, as an APFS clone where the disk allows (`COPYFILE_FICLONE`, else a normal copy), and the copy's SHA-256 must be its id. Only then is the backup given its name. An original that is missing or changed fails the backup visibly ("a document file is missing or changed"), and the previous good backup stays: a backup without a document is not a backup of the record. The database copy comes first, so every file it names was already on disk (intake syncs the bytes before any row points to them); a file added after the copy isn't in that backup and isn't named by it. Pruning keeps the newest of each of the last 7 days and 4 weeks that had a backup, and runs only after a new backup passed, so a long closure or a failing backup never removes the last good ones. Rufi makes a backup at every start, in the background, and then whenever the newest is a day old (looked at every hour). A stored backup counts as the last good one only while it still passes its check: Rufi checks the newest at start and every hour (the database fully; each original by its presence and size, since reading every document each hour would cost more than it finds; each original's hash is checked when the backup is made and again by a restore), a damaged or incomplete one is shown as a failure and never stops a new backup, and pruning counts only backups that pass. The backup status lives in memory: after a restart, the start's own backup finds a fault that is still there and shows it, so no failure file is needed and an old failure never hides a recovery. The cost: each start replaces that day's earlier backup, and a start on a large record copies and checks it while Rufi is in use. A backup never holds the sign-in, nor `chatgpt.json`: its host id finds the sign-in in the Keychain, so a copy that kept it on the same Mac would be signed in without the person. Nor the AI's files (`codex/`, `workspace/`), logs, locks, `core.json` (a live launcher secret), `models.json`, or `cache/` (display copies such as a HEIC's JPEG, made again when missing). Restore puts a checked backup into a folder that doesn't exist or is empty, holding that folder's `rufi.lock`, through `restoring/`, where each original is copied and its hash checked; the originals move into place, then it links the database in place (a link fails where a file exists; a rename would replace it). `installed.json` is written right after a database is first made; a folder with it and no database, or with `restoring/`, is refused at start, so a lost record never looks like a new install. The export reads the same kind of fixed copy, and holds each original that copy names (`files/<sha256>.<ext>`, stored without compression), each checked against its hash; a missing or changed one fails the export rather than leave it out. Considered: copying the whole data folder (brings back the sign-in, a stale launcher and the AI's queue, which can't be resumed in a new folder anyway); restoring in place (a failed restore could make things worse); a backup at login while Rufi is closed (a login item and a second process for a single person's Mac). The reason: the record is what can't be remade; everything else is remade by signing in or starting Rufi. The cost: a restored copy needs a sign-in and starts with the default model list, waiting messages don't come back, backups on the same Mac don't survive losing it (an off-Mac copy comes later), and an original damaged on disk is found by the hourly look only when its size changed (a restore always finds it). Clones share the disk's blocks with the originals, so they cost no space until a file changes, and protect against a mistake, not a failing disk.
