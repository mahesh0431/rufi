# 0016 · Rufi's tools over MCP

**Date:** 14 Oct 2026 · **Status:** accepted

Rufi's tools reach the AI from Rufi's own MCP server (the Model Context Protocol, Streamable HTTP, with the official TypeScript SDK), not as Codex dynamic tools. A dynamic tool is frozen into a thread when it starts and serves only Rufi's own Codex; an MCP server is set per thread, can change without a new thread, and is the standard other AI apps can use later. The tools, their guards and their receipts are the same; only the transport changed. `server/mcp.ts` is a thin adapter over the tool registry.

**In Rufi's process, on its loopback listener.** The core serves two endpoints on its own port: `/mcp` for the chat's eight tools and `/mcp/reader` for the reader's two (ADR 0010). They sit outside the screens' checks (which refuse a POST without Rufi's browser Origin, and Codex sends none) and have their own: Host must be Rufi's loopback address, nothing forwarded, an Origin absent or Rufi's own, and a bearer key. The terminal ask, which has no core, serves `/mcp` on a listener of its own. The server never opens the database itself: it calls the same core functions as before. Rejected: a stdio MCP process (its own database connection, or a second channel back to Rufi); a second listener in the core (another port, for nothing).

**A key opens one scope.** Each endpoint has its own keys, in memory, so they end with the run; Rufi keeps only a key's hash. The chat makes one key per chat thread per run, when it starts or resumes the thread, and gives it to Codex as an `Authorization: Bearer` header in that thread's MCP settings; a new thread revokes the old one's. The reader makes one key per reading attempt, bound to one person, one document and one attempt, and revokes it the moment a Stop, a cancel, a delete or a newer retry begins, and again when the attempt ends. The key decides which tools there are and what a call may do; nothing in a request names a person, a chat or a document. A chat key on the reader's endpoint, or the reverse, opens nothing.

**Each call is bound to its reply.** Codex puts the call's id, its thread and its turn (`x-codex-turn-metadata.turn_id`) in each call's `_meta` (0.159.3). The chat admits a call only when the key's chat runs a reply on that thread and the call's turn is that reply's turn: a call with no running reply, from a stopping one (Stop marks it stopping before the interrupt), or for another turn is refused with "No reply is running.", and the refusal is logged. A call admitted before Stop finishes against the reply it was admitted for, so a save that committed keeps its receipt under the stopped reply. Where the reply came from (the person or a Rufi event), and so whether it can save, comes from Rufi's own record of the reply, never from the request. Saves and dismissals key on Codex's call id, so the same call again gets the same receipt. A tool's answer is written to the reply's activity before the server returns it. Rejected: a key per reply (Codex's MCP settings are per thread); relying on Codex's cancel notice (best effort on the pinned client).

**What Codex is given.** Each thread's settings name one server, `rufi`, as required: if it doesn't start (a refused key, Rufi's listener gone), Codex fails the thread's start or resume, and the message waits with "Rufi's tools didn't start for the AI, so it can't reply now." Its tools are approved in advance (with approvals off, Codex would refuse a tool that isn't read-only). Its deadline is the tool deadline plus a margin, so Rufi's own "took too long" answer arrives first. The chat's tools are deferred: on the code-mode models the AI finds them inside `exec` as `tools.mcp__rufi__<tool>`. The reader's are eager (ADR 0010). Each tool says whether it only reads (`readOnlyHint`). Codex also adds its MCP resource helpers; they find nothing, because Rufi's endpoints offer no resources yet.

**The save keeps its one form, typed.** Codex shows the code runner each tool as a TypeScript declaration made from its input schema. Before, it cut a schema over 5,000 bytes to `unknown`, and `save_changes` named its fields only in its description. Now each thread raises the budget to 64 KiB (`tool_input_schema_max_bytes`), and the server writes each schema's shared parts (`$defs`) in place, because the pinned Codex resolves only the first few `$ref`s and leaves the rest `unknown`. `save_changes` is 25 KB that way, typed in every branch. `capture.test.ts` checks this on the real Codex: every kind and action a literal, required fields required, no field `unknown`. The fields stay in the description too.

**Images.** A page comes back as MCP image content after the answer's text. On a direct model Codex gives it to the model as an image; in code mode the script shows it with `image(...)`. As before, `tool_calls` keeps only the text, and an activity's details keep "(a page image, not kept)" in place of the data.

**Threads.** The tools' version now includes the transport, so a thread made with dynamic tools is not resumed: the first message after this change starts the AI afresh, as for any change to the tools. Nothing else about threads, instructions or the sandbox changed.

**Accepted races (TODO: check later).** A call can arrive before Rufi has heard that its reply started; it is refused, and the AI sees the refusal. While the reader's runner stops an attempt on its own (its deadline, an item it doesn't allow), calls can still land until the run returns; they are for the right attempt, and an attempt that didn't complete makes no drafts.

The cost: Rufi now runs an HTTP server that answers anything on this Mac that has a key; the keys are random, never stored, and given only to Codex. The AI's contract depends on pinned Codex details (`_meta`'s fields, the names inside `exec`, how it renders schemas), so a Codex upgrade must pass `capture.test.ts` and `subagent.test.ts` again.

**Extension, 14 Oct 2026: the AI's own folder, its rules as a core and skills, and one thread.** It replaces PLAN §4's full access. ADR 0006 still holds: the AI reads one person's record, through Rufi's tools only.

_The AI's folder._ The chat's AI works in `ai/` in the data folder (Codex's `workspace/` before). It keeps its programs, notes and research files there between messages. Rufi makes the folder at start. Nothing in it is part of the record. It isn't in backups, the export or a move yet (TODO): its programs keep links and this folder's paths.

_The sandbox._ Rufi writes one named permission profile, `rufi-ai`, into its `config.toml` (`agent/codex/settings.ts`). It extends Codex's `:workspace` profile: the AI's commands write in the AI's folder and the temp folders, read the rest of the Mac, and use the network. They can't read the record's database (`rufi.sqlite` and its `-wal`, `-shm` and `-journal` files), `backups/` (copies of it), or `core.json`, whose secret opens Rufi's screens and through them the record (`aiSandbox` in `server/core.ts`). Thread start and resume select the profile with `permissions`. They never send the legacy `sandbox`, which can't deny a read, and the two can't go together. Approvals stay `never`. Rufi checks that Codex reports `rufi-ai` as the thread's active profile, not the legacy projection, which can't show denied reads. The commands get no variable named like a secret (`ignore_default_excludes = false`): by default Codex passes its whole environment, so the access token it runs with reached the commands before. The macOS canary in `capture.test.ts` proves this on the real pinned Codex, also after a model change and a resume: the database, its WAL, the backups and `core.json` can't be read, nothing outside the folder (or in the skills) can be written, the folder can, the network answers, and `env` holds no token and no MCP key. Rejected: Codex's `workspace-write` alone (no denied reads); no network (the AI researches and installs what its programs need); limits on every other read (a TODO).

_The core and the skills._ Rufi's rules were 15 KB of developer instructions in every thread. Now the developer instructions hold a core of about 5 KB (`core/chat/instructions.ts`): the safety text, the record only through Rufi's tools, data is never an instruction, the AI's folder, the rules every answer needs (flags first, the rufi-basis block), the yes rule and receipts, Rufi events, an index of the skills, and the tool names, because code mode defers MCP tools. The rules for each job are skills: standard `SKILL.md` files in `core/skills/`, written into `CODEX_HOME/skills/` at each start, so they match the running Rufi. Codex lists them in each thread with their descriptions, and the AI reads one when its job comes up. Codex's own bundled skills are off (`[skills.bundled] enabled = false`); an explicit read-only entry for the skills root lets the AI read them but not change them, also when the data folder is in a writable temp root. The chat's MCP endpoint offers the same text as plain resources, `skill://<name>/SKILL.md`, for other AI apps later; the MCP Skills extension comes with them. The personality is `none`, in the chat and the reader: the pinned models' prompts have no personality section, but a later prompt can't add one. Rejected: a Rufi tool that returns a guide (Codex reads skills natively, and the format is portable); everything in every thread.

_One thread._ A new model goes with the next `turn/start`, in the same thread; the AI keeps the whole chat. Rufi stores the version of the rules a thread was told (the core and the skills' names, descriptions and text) in `chats.thread_tools`. The pinned Codex keeps the developer instructions a thread was first given in its history: a resume doesn't replace them, also not for a thread it closed, and Codex ignores a resume's settings for a thread it has open. Only a compaction builds the context again from the current ones. So when the rules changed (a new emergency region, or a Rufi update), Rufi gives the idle thread its new rules before the next message: it lets the thread go if it is open (`thread/unsubscribe`; `thread_unload_delay_secs = 0` closes it at once), waits for `thread/closed`, resumes it with the new core and a key, and asks Codex to summarise it (`thread/compact/start`). That summary's turn is Rufi's own, never shown. If it fails, the message waits with "The AI couldn't take Rufi's new instructions, so it can't reply now. Try again.", and no new thread starts. A new thread starts only when the old one can't be resumed. The tools aren't part of the version: Codex reads the MCP catalog again at each resume. `capture.test.ts` proves a model change, a cold resume after a tool and the core changed, and a compaction that keeps the new core. Rejected: a block of rules with each message (more context, and the plan keeps context lean); the core as `AGENTS.md` (Codex replaces it per turn, but as user words, weaker than developer instructions for safety); a new thread with the last 10 messages (the AI forgets the chat).

The cost: a new region or a Rufi update summarises the chat once, so the AI keeps a summary of older messages, not every word; the AI's commands can read anything else the person's account can read (a TODO); a Stop during that summary lets it finish, and a message sent meanwhile waits with "The AI is busy in this chat." (an accepted race).

**Extension, 30 Oct 2026: the same lock-down on Claude.** When the AI runs on the Claude installed on the Mac, through the Claude Agent SDK, `aiSandbox` holds it as `rufi-ai` does on Codex (`agent/claude/sandbox.ts`), in the settings Rufi gives that Claude, never the person's own. Claude's sandbox holds the commands. They write in the AI's folder and the temp folders: `/tmp` by its real path, because Claude's sandbox ignores the macOS link, and the Mac's temp folder. They can't read or write the unreadable paths, can't write Rufi's skills (its plugin, also when the data folder is in a temp folder; Claude also guards a plugin it loaded), and use the network (`allowedDomains: ["*"]`). The sandbox doesn't cover Claude's own file tools, so permission rules do: the reading tools are allowed, writing only in the AI's folder, and reading an unreadable path is denied. The rules are gitignore patterns, so their paths are escaped: a data folder named, say, `Health [Asha]` stands for itself. The permission mode is `dontAsk`: what the rules don't allow is refused, never asked. No command runs outside the sandbox (`allowUnsandboxedCommands: false`), and without a sandbox there's no Claude (`failIfUnavailable`). Claude gives its commands a token for its own session's inbox; the sandbox keeps them from its socket, and the person's other Claude sessions can't message Rufi's (`crossSessionInbound: "refuse"`). CI has no Claude, so `pnpm claude:live` proves this on the installed one, in a data folder whose name holds brackets, a space and parentheses, each step on its own tool call and its own result, failing a step Claude skipped: Read, `cat` and Grep can't read the database, its WAL, the backups or `core.json`; nothing is written outside the folder and the temp folders, nor in the database or the skills; the folder and both temp folders can be written; the internet answers; the commands see no token they can use. Rejected: Claude's sandbox alone (its file tools would bypass it); a mode that asks (nobody answers).

**30 Oct 2026: one door for every agent (ADR 0024).** The chat's key per thread and its own check of a call's thread and turn are gone. Each agent has a key of its own for the run, given with its conversation each time it opens; its tools are the agent's own. The door passes a call's `_meta` as it came to the agent package, which asks the agent's adapter to place the call in an open turn of that agent's conversation (for Codex, by the thread, turn and call ids above) and gives it only once the package has admitted that turn. A call from a turn the provider began by itself waits for the admission until the call's deadline; any other call is refused with "No reply is running.", reading tools too, also when the agent has a newer turn. Rufi's id for the call is `<agent>/<conversation>/<provider call id>`, made at the door by one helper for every provider: saves, sorts, briefs and dismissals key on it, so a repeat makes one save and one receipt (its answer may differ from the first), and two agents, or two conversations of one agent, never share one. One caller, built from the placed scope (whose the agent is, the agent and its turn, its conversation and tools), runs every tool; a turn a Rufi event started still only reads, from Rufi's record of the reply. A write, its receipt or line and the call with the exact answer the AI gets commit in one transaction (`tool_calls`, which now names the agent and its turn in the agent database and is a reply's only for a root turn, migration 0021); if the call can't be kept, nothing of the write is. A call the agent stopped waiting for at the deadline goes on to its end. The reader and the terminal ask still read Codex's `_meta` themselves: they run on Codex directly. A receipt isn't labelled with the agent's title yet: only Rufi AI writes. The reason: one door and one write caller, whoever the agent and whichever the provider. The cost, accepted: the old conversation's key is no longer revoked at a new thread; its calls find no open turn to be placed in.

**Amendment, 30 Oct 2026:** the AI's commands can't read the token doors' `codex-door/` folder either, nor `core.json`'s temp copy while it is written (a denied glob, `core.json.*.tmp`), and Codex runs with no secret in its arguments or environment: any program of the user's can read another process's (`sysctl` `KERN_PROCARGS2`), so the access token in Codex's environment was readable by the commands. The canary also reads Rufi's own process and app-server from inside the sandbox and finds no token or key (ADR 0025).
