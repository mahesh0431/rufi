# 0016 · Rufi's tools over MCP

**Date:** 14 Oct 2026 · **Status:** accepted

Rufi's tools reach the AI from Rufi's own MCP server (the Model Context Protocol, Streamable HTTP, with the official TypeScript SDK), not as Codex dynamic tools. A dynamic tool is frozen into a thread when it starts and serves only Rufi's own Codex; an MCP server is set per thread, can change without a new thread, and is the standard other AI apps can use later. The tools, their guards and their receipts are the same; only the transport changed. `server/mcp.ts` is a thin adapter over the tool registry.

**In Rufi's process, on its loopback listener.** The core serves two endpoints on its own port: `/mcp` for the chat's eight tools and `/mcp/reader` for the reader's two (ADR 0010). They sit outside the screens' checks (which refuse a POST without Rufi's browser Origin, and Codex sends none) and have their own: Host must be Rufi's loopback address, nothing forwarded, an Origin absent or Rufi's own, and a bearer key. The terminal ask, which has no core, serves `/mcp` on a listener of its own. The server never opens the database itself: it calls the same core functions as before. Rejected: a stdio MCP process (its own database connection, or a second channel back to Rufi); a second listener in the core (another port, for nothing).

**A key opens one scope.** Each endpoint has its own keys, in memory, so they end with the run; Rufi keeps only a key's hash. The chat makes one key per chat thread per run, when it starts or resumes the thread, and gives it to Codex as an `Authorization: Bearer` header in that thread's MCP settings; a new thread revokes the old one's. The reader makes one key per reading attempt, bound to one person, one document and one attempt, and revokes it the moment a Stop, a cancel, a delete or a newer retry begins, and again when the attempt ends. The key decides which tools there are and what a call may do; nothing in a request names a person, a chat or a document. A chat key on the reader's endpoint, or the reverse, opens nothing.

**Each call is bound to its reply.** Codex puts the call's id, its thread and its turn (`x-codex-turn-metadata.turn_id`) in each call's `_meta` (0.159.3). The chat admits a call only when the key's chat runs a reply on that thread and the call's turn is that reply's turn: a call with no running reply, from a stopping one (Stop marks it stopping before the interrupt), or for another turn is refused with "No reply is running.", and the refusal is logged. A call admitted before Stop finishes against the reply it was admitted for, so a save that committed keeps its receipt under the stopped reply. Where the reply came from (the person or a Rufi event), and so whether it can save, comes from Rufi's own record of the reply, never from the request. Saves and dismissals key on Codex's call id, so the same call again gets the same receipt. A tool's answer is written to the reply's activity before the server returns it. Rejected: a key per reply (Codex's MCP settings are per thread); relying on Codex's cancel notice (best effort on the pinned client).

**What Codex is given.** Each thread's settings name one server, `rufi`, as required: if it doesn't start (a refused key, Rufi's listener gone), Codex fails the thread's start or resume, and the message waits with "Rufi's tools didn't start for the AI, so it can't reply now." Its tools are approved in advance (with approvals off, Codex would refuse a tool that isn't read-only). Its deadline is the tool deadline plus a margin, so Rufi's own "took too long" answer arrives first. The chat's tools are deferred: on the code-mode models the AI finds them inside `exec` as `tools.mcp__rufi__<tool>`. The reader's are eager (ADR 0010). Each tool says whether it only reads (`readOnlyHint`). Codex also adds its MCP resource helpers; they find nothing, because Rufi's endpoints offer no resources yet.

**The save keeps its one form, typed.** Codex shows the code runner each tool as a TypeScript declaration made from its input schema. Before, it cut a schema over 5,000 bytes to `unknown`, and `save_changes` named its fields only in its description. Now each thread raises the budget to 64 KiB (`tool_input_schema_max_bytes`), and the server writes each schema's shared parts (`$defs`) in place, because the pinned Codex resolves only the first few `$ref`s and leaves the rest `unknown`. `save_changes` is 25 KB that way, typed in every branch. `capture.test.ts` checks this on the real Codex: every kind and action a literal, required fields required, no field `unknown`. The fields stay in the description too.

**Images.** A page comes back as MCP image content after the answer's text. On a direct model Codex gives it to the model as an image; in code mode the script shows it with `image(...)`. As before, `tool_calls` keeps only the text, and an activity's details keep "(a page image, not kept)" in place of the data.

**Threads.** The tools' version now includes the transport, so a thread made with dynamic tools is not resumed: the first message after this change starts the AI afresh, as for any change to the tools. Nothing else about threads, instructions or the sandbox changed.

**Accepted races (TODO: check later).** A call can arrive before Rufi has heard that its reply started; it is refused, and the AI sees the refusal. While the reader's runner stops an attempt on its own (its deadline, an item it doesn't allow), calls can still land until the run returns; they are for the right attempt, and an attempt that didn't complete makes no drafts.

The cost: Rufi now runs an HTTP server that answers anything on this Mac that has a key; the keys are random, never stored, and given only to Codex. The AI's contract depends on pinned Codex details (`_meta`'s fields, the names inside `exec`, how it renders schemas), so a Codex upgrade must pass `capture.test.ts` and `subagent.test.ts` again.
