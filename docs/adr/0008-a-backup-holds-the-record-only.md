# 0008 · A backup holds the record only, and Rufi never starts over without it

**Date:** 8 Oct 2026 · **Status:** accepted

A backup is `rufi.sqlite` alone: SQLite's online copy, made in one step (one read of the database, so a save is in it whole or not at all) into a new private staging folder in `backups/`, made a single file, checked (it opens as Rufi's schema, `integrity_check` and `foreign_key_check` pass, and its size and hash match its own `backup.json`), and only then given its name. Pruning keeps the newest of each of the last 7 days and 4 weeks that had a backup, and runs only after a new backup passed, so a long closure or a failing backup never removes the last good ones. A stored backup counts as the last good one only while it still passes its check: Rufi checks the newest at start and every hour, a damaged or incomplete one is shown as a failure and never stops a new backup, and pruning counts only backups that pass. The last failed try is kept in `backup-failed.json` until a backup succeeds, so a restart never hides it; a file that can't be read shows as a failure, never as success. A backup never holds the sign-in, nor `chatgpt.json`: its host id finds the sign-in in the Keychain, so a copy that kept it on the same Mac would be signed in without the person. Nor the AI's files (`codex/`, `workspace/`), logs, locks, `core.json` (a live launcher secret) or `models.json`. Restore puts a checked backup into a folder that doesn't exist or is empty, holding that folder's `rufi.lock`, through `restoring/`, and links the database in place (a link fails where a file exists; a rename would replace it). `installed.json` is written right after a database is first made; a folder with it and no database, or with `restoring/`, is refused at start, so a lost record never looks like a new install. The export reads the same kind of fixed copy. Considered: copying the whole data folder (brings back the sign-in, a stale launcher and the AI's queue, which can't be resumed in a new folder anyway); restoring in place (a failed restore could make things worse); a backup at login while Rufi is closed (a login item and a second process for a single person's Mac). The reason: the record is what can't be remade; everything else is remade by signing in or starting Rufi. The cost: a restored copy needs a sign-in and starts with the default model list, waiting messages don't come back, and backups on the same Mac don't survive losing it (an off-Mac copy comes later). Original files join backups when Rufi stores them.
