# 0004 · Rufi keeps the conversation; the agent keeps its working state

**Date:** 4 Oct 2026 · **Status:** accepted

Each conversation's transcript is Rufi's own, in `rufi.sqlite`, stored before anyone is shown it: the user's messages (steers marked), one activity line for each thing the AI did (its kind, a short title, one short detail, done, failed or stopped, and when), the AI's replies, saved as they grow, with the model and how each reply ended, and a receipt entry for each save to the record, written in the save's own transaction (docs/adr/0005). Since M2.3 the transcript also keeps, with the conversation, everything the agent gave about each activity (what it sent and got back, as the agent's own JSON, replaced when the activity ends), the AI's reasoning summaries (Rufi asks Codex for them), and Rufi's own record of each call to its tools with exactly the answer the AI got (`tool_calls`); none of these is shown yet, except as an answer's Used (docs/adr/0007) and the reasoning summaries, which are saved as they grow and shown as the AI's thinking. Streaming chunks and the agent's sub-agent work are not saved; the agent keeps them in its own thread while that thread lives. The agent's thread is only a pointer: Rufi starts a new one when the model, the agent or Rufi's tools change, or when a thread can't be resumed, and gives it the last 10 messages with a note (a reply that didn't finish goes as its answer only, marked so); the `read_conversation` tool pages back through the rest. Messages sent during a reply wait in the agent's own queue (Codex `thread/queue/*`), not in a Rufi queue: Rufi saves each message when the agent starts it, by the id Rufi gave it, and after a crash fills a missing one from the agent's thread, never running it again. Stop pauses that queue; the next Send starts it again, oldest first. Before the agent has a message, Rufi's only copy is the conversation's draft: a send holds it (state `sending`, with the message's id) in one short commit before it asks the agent, so no save or other send can change it, and it is emptied when the agent took the message or returned to edit when the agent refused it. If Rufi stops meanwhile, it looks for that id in the transcript when it starts: found, the draft is emptied; not found, the text stays as `unknown` and the person is told to check the conversation. It is never sent again by itself: this is the one delivery state Rufi keeps, not a queue. The reason: a conversation survives a change of agent or model, and Rufi stores nothing it can't show or explain. The cost: a new thread knows only the last 10 messages until the AI reads further, and what waits lives in the agent's files. Saving sub-agent work, and how long the full activity is kept, are still open.

**8 Oct 2026, M2.5: one chat.** Each person has exactly one chat, made with them in the same transaction, and never a second (`chats.person_id` is unique), so two tabs never make two; there is no list, name, choice or per-chat address, and the user changes the subject by saying so. The transcript, turns, saves, drafts and waiting messages keep their links to it, and whose data it is doesn't change. The screens read the transcript by pages, not whole: a page is a range of `seq`, widened down to whole turns, with every entry in the range (also one of no turn) and the turns with no entry that started in its time, so pages never skip or repeat; older pages are read by a `seq` cursor, a newer read of an entry or turn always wins, and a reconnect replaces what is loaded with the latest page. Where the AI started afresh is worked out when the chat is shown, not stored: each turn keeps the agent thread it ran on, written with the turn, and a turn on another thread than the one before shows a quiet line; a compaction the agent completed is stored as its own activity and shows the same line. `read_conversation` is now `read_chat`. The schema was reset, with no migration: a backup from before is refused as from an older Rufi. The reason: one helper, one chat, and a chat of months must still open fast. The costs, accepted: a crash between a new thread and its first message loses the last-messages note (the AI can still read the chat), and a compaction finished while Rufi was down shows no line.

**9 Oct 2026: the last save wins for drafts.** A draft has no revision: each save replaces the text, so two tabs typing at once may replace each other's unsent text, and nothing is merged or refused but by a send's hold. Each tab still saves one at a time, so an old answer never overwrites its newer typing, and a save whose answer was lost is saved again. A send saves first, then the core keeps the sent text as the draft and holds it in one commit, so what is held is what is sent; the hold, `unknown`, the recovery at start and never sending again stay as above. One module owns the draft and its send on each side: `core/chat/drafts.ts` and the screens' `draft.ts`. The schema was reset. The reason: one person on one Mac doesn't need conflict handling for unsent text, and it cost a protocol of its own. The cost, accepted: text typed in two tabs at once can be lost, without a trace.

**10 Oct 2026, M3: Rufi owns the queue; Rufi events.** What waits to go to the AI is Rufi's, in `chat_queue`, no longer the agent's (Codex's own queue isn't used): the person's messages and the notes of Rufi events, in one order. A send moves the box's text into a new row and empties the draft in one transaction; the row's id is the send's own, so a retried send finds its row and never makes a second, and it becomes the message's id in the transcript. The draft's `sending` hold and `unknown` state are gone. Rufi hands the AI one turn's rows at a time: it claims them in the database (`handing_over`) before it calls the agent's turn start, and the next only after that turn and its transcript writes have ended. The turn's start marks its rows sent and writes the person's message, with the turn and its origin, in one transaction. A hand-over the agent surely didn't get (Rufi never asked, or the agent refused) waits again, the person's held with the reason; one nobody knows the end of, or one Rufi stopped during, is `not_sure`: shown, never sent again by itself, and the chat pauses, because the agent's turn start steers into a turn that runs, so Rufi must never start one blind. Steer goes straight into the running turn; if it has ended, the steer is refused and its text stays in the box. Stop stores a pause (`chats.paused`) before it interrupts; only the person's next send (or Send now) ends it, never a sign-in or an event, and Rufi starting with rows waiting pauses the chat the same way. Signed out, and rows restored from a backup, stay held until the person sends or removes them. Waiting rows go to a new model. A Rufi event is Rufi's: its producer writes, in one transaction with its own outcome, a transcript line of kind `event` and, when the AI should hear of it, a queue row with origin Rufi. Event rows waiting next to each other go to the AI together, in one turn whose origin is Rufi; in it the tool host refuses `save_changes` (and later every other change), so an event is never the person's words or their yes. An event that comes while the chat is paused or signed out rides with the person's next message, marked used by that turn in the same step, never a turn of its own later. Origins are stored on turns and queue rows and used by the live transcript, gap recovery (a hand-over found in the agent's record fills its rows by origin), `read_chat` and a fresh thread's history. The reason: one queue that Rufi can show, keep safe across restarts, backups and model changes, and mix with its own events. The cost, accepted: Rufi now keeps a delivery state machine of its own; a steer can land in the next turn when the dispatcher starts it just after the person saw the last one end (TODO: check); a crash between Codex starting a turn and Rufi saving its start leaves the rows "not sure" until the thread is read again. The schema was reset.

**14 Oct 2026: a new thread only when the old one is lost (ADR 0016).** A new model goes with the next reply, in the same thread, and new rules or tools reach the thread without a new one. Rufi starts a new thread, with the last 10 messages, only when the chat's thread can't be resumed (for example after a restore or a move).

**17 Oct 2026: signed out, a send takes nothing.** Signed out is an ordinary error, not a reason to hold: the core refuses the person's send (and Send on a held row) without a sign-in, so nothing is queued and the text stays in the box, which offers Sign in; after signing in the person sends again. Rufi events that come while signed out still ride with the next message. A message Rufi took before the sign-in went away keeps waiting, not held: signing in alone sends nothing, and it goes at the next hand-over, which the person's next send or a Rufi event can start. A person's row an older Rufi held `signed_out` stays held, with no reason of its own, until it is sent or removed.

**17 Oct 2026: a new thread and a compaction have their own lines.** A turn on another thread than the one before shows "New thread started"; a compaction shows "Compacting chat history…" while it runs and "Chat history compacted" once done. When a new thread starts, and how the AI gets new rules, is ADR 0018.

**18 Oct 2026: Rufi's own request to sort a file (ADR 0019).** The one exception to "nothing goes to the AI until the person sends": when a reading ends, Rufi asks Rufi AI to sort the file it read. Its row goes in a turn of its own, never rides with the person's message, and isn't held by the pause after a restart (a hand-over a restart cut off waits again, since `sort_documents` does it once). In that turn the tool host lets the AI sort that file and nothing else. A Stop still holds it until the person sends; a restore ends it, for Retry.

**24 Oct 2026: files start on Send (ADR 0022).** The sorting exception above is gone. A person's message sends its files; Rufi copies their pages in that reply, then Rufi AI sorts and answers. Nothing starts when a file is chosen. Rufi-started replies still carry factual notes, such as a deleted document, and cannot sort or save.

**30 Oct 2026: Rufi AI's steps live in the agent database (ADR 0024).** For new replies, the activity lines (with everything the agent gave about each), the AI's notes and its reasoning summaries are kept in `agents.sqlite`, not in the transcript. The screens read them from there, merged into their reply after what the reply started with, and the stream shows them as they come; a note's or a summary's text is saved once whole, or as far as it came when the reply ends, and until then the agent system gives it from what it holds. The transcript keeps the person's messages, the AI's answers, receipts, events and Rufi's own reading steps; a question the AI asks is kept apart from its answer's text (`transcript_entries.questions`), so an answer made whole from the agent system's events never drops it. Replies from before keep their lines. The reason: Rufi's database holds what the person asked and what the AI answered. The costs, accepted: losing `agents.sqlite` loses the Activity of the replies since; a picture or a compaction line shows right after what its reply started with, not where it came; a fresh thread's history no longer has the AI's notes.

**30 Oct 2026: Rufi AI's queue hands over (ADR 0024).** What waits stays Rufi's, in `chat_queue`, and Rufi says what goes; the agent package starts each turn. Rufi's waiting rows go into Rufi AI's queue in the agent database by id, in Rufi's order, and an edit, a removal, a new order or a Send goes to Rufi first. Before a turn starts, the package asks Rufi for the row's words: Rufi claims the row (`handing_over`, with `sent_as` naming the agent's conversation) and gives its words as they are then, so an edit before the claim goes and one after is refused. The same conversation asking again gets the same words; a row removed or held is gone. A crash after the claim and before the hand-over leaves the row claimed: at the next start the package asks again and sends it once. Each row is an input and a turn of its own: a Rufi note no longer rides with the person's message, nor goes with other notes. A message with files waits in Rufi until its reading ends, and those behind it wait too; the reading starts once it is next and Rufi AI is idle. The pause after a Stop or a restart (`chats.paused`) is gone: Stop ends only the reply, and what waits goes on; a message whose start the Stop cut off is held, "Not sent: stopped.", for Send or remove. A row an older Rufi was handing over to the AI is "not sure" (migration 0020). Messages sent while a reply runs still go into it as today. The reason: one dispatcher, the package's, and a Stop that does only what it says. The cost, accepted: after a Stop, a message the person wanted to hold back goes unless they remove it, and what waited when Rufi closed goes when it starts.

**30 Oct 2026: a message sent while a reply runs is a queue row too.** Every send saves its row and empties the draft in one transaction, before anything goes to the AI; the chat shows it at once, after its last message, marked waiting, with edit, a new order, Send now and Remove. While a reply the person started runs, a new message of theirs with nothing to read goes into Rufi AI's queue as a steer, also past what waits; the package claims its words from Rufi like any other row, and a steer that misses its turn starts the next one. Its words no longer wait in memory, so a crash before the AI took it leaves it in the queue: it goes once at the next start, or is "not sure" if Rufi may have handed it over. Its line in the chat is written, as a steer, when the package reports it taken into a running turn. The reason: one lasting copy of every message the person sends. The cost: a message sent mid-reply shows as waiting for a moment before it is in the reply.

**31 Oct 2026: the person chooses steer or queue.** A message sent while a reply starts or runs goes as the person chooses, kept with its row (`chat_queue.kind`): a steer goes into that reply once it runs; a queued one waits for a reply of its own. Enter does what Settings says (`while_replying`, steer by default); the box's other button does the other, and a waiting message can be steered. Rufi no longer decides by itself, also not for a message sent while the reader copies. A steered message reaches the AI after one line saying it is being steered; the person sees their own words. A message counts as sent once handed to the AI (ADR 0024): one Rufi couldn't hand over shows "Failed" with the error as it came, or "Not sent" when Stop cut its start off, and goes when the person sends it. Send now is gone: Steer replaces it.
